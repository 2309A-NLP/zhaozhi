# 角色扮演系统优化文档

## 1. 文档说明

本文档基于当前项目实际实现整理，目标是为后续迭代提供一份可执行的优化方案，覆盖性能、稳定性、可维护性、可观测性和产品体验五个方面。

项目主体位于 `研发` 目录，当前系统已经具备完整的角色对话、知识文档上传、RAG 检索和多轮会话能力，但随着数据量、并发量和部署复杂度提升，现有实现还有较大的优化空间。

## 2. 当前系统优化目标

本项目后续优化建议围绕以下目标展开：

- 提升聊天接口响应速度
- 提升文档入库与检索效率
- 降低 Redis、Milvus、LLM 异常时的抖动和资源浪费
- 提高系统可维护性和可观测性
- 为后续多用户、多文档、多角色扩展预留空间

## 3. 当前现状概览

从代码实现来看，当前系统具备以下特点：

- 后端采用 `FastAPI`
- 前端同时存在 `Streamlit` 工作台和静态前端
- RAG 主链路由 `ChatService + RAGEngine` 组织
- 文档上传后会同时写入 Milvus 和本地 `MilvusIndex`
- 会话记忆优先 Redis，不可用时退回进程内存
- LLM 不可用时会返回 fallback answer

这些设计保证了系统“能跑、能降级、能演示”，但也带来一些可优化点：

- 检索链路存在重复计算
- 本地回退检索偏粗糙
- 大模型、向量模型、重排模型的资源使用策略还比较朴素
- 前端并发和缓存策略仍偏轻量
- 缺少更系统的日志、监控和指标体系

## 4. 优化优先级建议

建议将优化分为三个阶段推进：

### P0：优先立即处理

- 聊天主链路性能优化
- 本地回退检索质量优化
- 敏感配置与部署安全优化
- 关键日志与异常信息补强

### P1：中期优化

- 模型加载与推理资源优化
- 文档处理与索引构建优化
- 数据库访问与查询优化
- 前端缓存与并发策略优化

### P2：长期演进

- 引入指标监控与链路追踪
- 引入更完整的异步任务体系
- 引入长期记忆和检索评估体系
- 统一前端技术形态

## 5. 核心性能优化

### 5.1 聊天主链路优化

#### 当前现状

当前聊天主链路大致为：

1. 读取短期记忆
2. 构造搜索 query
3. 生成 query 的 dense/sparse 向量
4. 走 Milvus 混合检索
5. 失败时走本地回退检索
6. 重排
7. 调用 LLM
8. 写入记忆和会话记录

#### 主要问题

- 检索、重排、LLM 生成串行执行，整体耗时受最长链路影响明显
- 回退检索命中后，仍可能返回相关性较弱的块
- 对同一会话连续提问时，没有利用更细粒度的检索缓存

#### 优化建议

1. 为聊天链路增加阶段耗时统计。
2. 为相同 `session_id + message` 增加短期结果缓存。
3. 把“查询改写 / 检索 / 重排 / 生成”耗时拆开记录，识别真实瓶颈。
4. 在 `RAGEngine` 层面引入候选集缓存，减少连续提问时的重复向量化和重复召回。

#### 预期收益

- 更快定位慢点
- 降低重复问题的响应耗时
- 降低模型与向量检索重复开销

### 5.2 本地回退检索优化

#### 当前现状

当前本地回退检索主要依赖 `MilvusIndex.chunk_text` 和 `Document.content` 的切块结果，回退逻辑可用，但排序策略较弱。

#### 主要问题

- `_local_search()` 主要按 `doc_id` 和 `chunk_index` 顺序取前 `top_k`
- 回退检索没有先做关键词相关性打分
- 大文档场景下，本地回退结果可能与问题不够贴近

#### 优化建议

1. 在本地回退检索中增加简单相关性评分。
2. 对 `chunk_text` 做词项匹配、覆盖率或 BM25 风格排序。
3. 先取候选块，再统一交给 reranker，而不是直接按顺序截断。
4. 为本地检索增加命中日志，记录命中块数、排序分数和最终返回内容。

#### 预期收益

- Milvus 异常时回答质量更稳定
- 回退模式下更少出现“答非所问”

### 5.3 文档切块策略优化

#### 当前现状

当前分块策略基于固定的 `CHUNK_SIZE=500` 和 `CHUNK_OVERLAP=80`。

#### 主要问题

- 固定参数对不同类型文档不一定最优
- PDF、医疗指南、法规文本等长段落文档可能切块过粗
- 对 FAQ、结构化文档可能切块过细或重复度过高

#### 优化建议

1. 按文档类型区分切块策略。
2. 对标题、段落、编号、表格内容做结构感知切块。
3. 为切块策略增加实验配置，便于比较不同参数效果。
4. 对 `chunk_count`、平均块长、重复率做统计分析。

#### 预期收益

- 提高召回精度
- 减少无效 chunk 数量
- 降低向量存储与重排成本

## 6. 模型与推理优化

### 6.1 向量模型加载优化

#### 当前现状

嵌入模型通过全局单例方式延迟初始化，能避免重复实例化，但缺少更细粒度的运行状态管理。

#### 主要问题

- 首次请求冷启动成本较高
- 模型初始化失败后缺少明显告警
- 不同模块分别维护 `_embedding`，重复管理成本高

#### 优化建议

1. 将 embedding 模型实例管理进一步集中化。
2. 启动阶段增加模型预热选项。
3. 增加模型当前后端信息日志，如 `bgem3 / sentence_transformer / fallback`。
4. 对失败回退到 fallback 的场景增加显式告警。

#### 预期收益

- 降低首问延迟
- 提升模型状态可观测性
- 降低多模块重复维护成本

### 6.2 重排模型优化

#### 当前现状

reranker 已支持 `FlagEmbedding`、HuggingFace 和 fallback 三种后端。

#### 主要问题

- 候选集规模大时，重排耗时会线性上升
- 当前没有根据场景动态调整是否启用重排
- fallback 重排仅基于词重叠，效果有限

#### 优化建议

1. 引入“候选集阈值控制”，只对前 N 个候选做重排。
2. 为角色或知识域配置重排开关。
3. 对低风险、低复杂度场景支持“跳过重排”的轻量模式。
4. 为重排阶段记录候选数量与耗时。

#### 预期收益

- 降低平均响应耗时
- 在性能和质量之间做更灵活的权衡

### 6.3 LLM 调用优化

#### 当前现状

LLM 调用采用同步 SDK，再通过 `asyncio.to_thread()` 包装进异步流程。

#### 主要问题

- 高并发下线程切换会带来额外开销
- 当前重试次数较少，超时策略偏硬
- 缺乏对不同模型、不同场景的调用策略区分

#### 优化建议

1. 为不同角色或场景设置不同的 `max_tokens / timeout / retry`。
2. 对短问短答场景使用更轻模型或更短超时。
3. 为超时、失败、fallback 比例增加统计。
4. 视后续规模决定是否切换为真正异步的 LLM 客户端适配层。

#### 预期收益

- 更稳定的响应时延
- 减少资源浪费
- 更容易做成本控制

## 7. 数据层优化

### 7.1 数据库查询优化

#### 当前现状

当前数据库结构清晰，仓储层职责明确，但查询优化仍偏基础。

#### 主要问题

- 文档列表、角色列表、会话写入暂未形成完整的分页与归档策略
- 本地回退检索时可能一次读出较多 chunk
- 会话表未来增长后，单表压力会逐步上升

#### 优化建议

1. 为文档、角色、会话列表接口增加分页能力。
2. 为高频查询字段补充索引评估。
3. 为 Conversation 增加按用户、角色、时间维度的检索策略。
4. 定期归档历史会话记录，避免主表无限增长。

#### 预期收益

- 降低数据库读取压力
- 提升列表和检索场景稳定性

### 7.2 文档与会话存储优化

#### 当前现状

文档全文直接存入数据库，聊天记录也完整存入 `Conversation` 表。

#### 主要问题

- 长文档和长对话会持续推高存储体积
- 对话向量化与结构化存储重复存在，后续需要规划数据保留策略

#### 优化建议

1. 明确“全文存储”和“检索切块存储”的保留策略。
2. 对历史会话考虑冷热分层。
3. 对 `retrieved_docs` JSON 字段做长度控制或摘要化。

#### 预期收益

- 降低数据库膨胀速度
- 提高后期维护性

## 8. 缓存与并发优化

### 8.1 Redis 使用优化

#### 当前现状

Redis 当前主要用于短期记忆，连接超时时间设置较短，有利于快速降级。

#### 主要问题

- Redis 只用于消息记忆，尚未利用其做热点缓存
- 当 Redis 波动时，系统会频繁退回内存模式

#### 优化建议

1. 使用 Redis 缓存热门角色配置、健康检查结果或常用文档列表。
2. 为 Redis 降级增加状态标记，避免短时间内反复重试。
3. 对 Redis 异常次数和恢复次数做计数。

#### 预期收益

- 提高稳定性
- 减少无效重试

### 8.2 前端并发优化

#### 当前现状

多角色模式下，`frontend_shared.py` 使用 `ThreadPoolExecutor` 并发请求聊天接口。

#### 主要问题

- 线程池大小固定为 `4`
- 前端请求层没有做更细的熔断和重试控制
- `documents_cache` 只有基础刷新，没有更细粒度的过期策略

#### 优化建议

1. 让并发数可配置。
2. 为多角色并发请求增加超时和失败提示聚合。
3. 为文档缓存增加 TTL 或主动失效机制。
4. 避免每次操作后都全量刷新文档列表。

#### 预期收益

- 改善多角色模式下的用户体验
- 减少前后端无效交互

## 9. 稳定性与安全优化

### 9.1 配置安全

#### 当前现状

项目当前通过 `.env` 管理密钥和运行参数。

#### 主要问题

- 开发环境可能保留真实 API Key
- 模型路径和密钥可能存在机器绑定或泄漏风险

#### 优化建议

1. 清理仓库中的真实密钥。
2. 区分开发、测试、生产环境配置。
3. 为配置加载增加合法性校验。

### 9.2 CORS 与接口暴露

#### 当前现状

当前后端采用较宽松的 CORS 配置。

#### 主要问题

- `allow_origins=["*"]` 与 `allow_credentials=True` 组合在生产环境不合适
- 容易带来跨域安全风险和行为不确定性

#### 优化建议

1. 生产环境明确白名单域名。
2. 将开发环境与生产环境 CORS 策略分离。

### 9.3 异常处理优化

#### 当前现状

当前不少异常分支已做 fallback，但记录粒度仍不够细。

#### 优化建议

1. 为 Redis、Milvus、LLM 三类降级分别增加独立日志。
2. 对超时、空结果、模型加载失败做结构化记录。
3. 在接口层对关键异常返回更明确的错误码或错误原因。

## 10. 可观测性优化

### 10.1 日志体系

建议增加以下日志维度：

- 请求 ID
- 用户 ID
- 角色 ID
- session_id
- 检索耗时
- 重排耗时
- LLM 生成耗时
- fallback 类型

### 10.2 指标体系

建议至少监控以下指标：

- `/api/chat/` 平均响应时间
- 文档上传平均耗时
- Milvus 命中率
- 本地回退检索占比
- Redis 降级占比
- LLM 超时率
- LLM fallback 占比

### 10.3 链路追踪

中长期建议为聊天主链路增加统一 trace id，便于排查：

- 某次请求慢在哪里
- 是检索慢还是生成慢
- 是 Redis/Milvus 异常还是模型超时

## 11. 工程与代码结构优化

### 11.1 模块职责继续收敛

建议继续保持当前分层结构，同时做以下增强：

1. 将模型实例管理进一步收敛到统一工厂。
2. 将通用 fallback 策略抽为更清晰的公共工具。
3. 将性能配置、降级配置从通用配置中再细分一层。

### 11.2 测试体系完善

建议补充：

- 服务层单元测试
- 文档上传链路测试
- 聊天接口集成测试
- Redis / Milvus / LLM 降级测试
- 检索质量回归测试

### 11.3 数据迁移能力

当前数据库主要靠启动建表，建议后续引入：

- 数据库迁移脚本
- 表结构版本管理
- 生产环境变更审计流程

## 12. 产品体验优化

### 12.1 前端体验

建议优化：

- 聊天中增加明确的“检索中 / 生成中 / 降级中”状态
- 多角色并发回复时增加进度反馈
- 文档上传后显示更清晰的切块数量和处理结果

### 12.2 结果可解释性

建议优化：

- 更清晰展示命中的知识片段来源
- 区分“Milvus 检索命中”和“本地回退命中”
- 当使用 fallback answer 时给出更明确提示

## 13. 推荐优化路线图

### 第一阶段：1 到 3 天

- 增加聊天链路耗时日志
- 优化本地回退检索排序
- 清理密钥与环境配置
- 收紧生产环境 CORS

### 第二阶段：3 到 7 天

- 增加 Redis / Milvus / LLM 降级统计

## 14. 结论

当前项目的优势在于业务闭环完整、降级链路清晰、研发迭代速度快，因此它已经具备继续扩展和优化的良好基础。

如果从投入产出比来看，最值得优先做的不是大规模重构，而是先把“聊天主链路耗时可见、本地回退更聪明、配置更安全、日志更清楚”这四件事做好。这样既能快速提升系统质量，也能为后续更深层的模型优化、检索优化和工程优化打下稳定基础。
