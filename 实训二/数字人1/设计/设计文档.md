# Linly-Talker 设计文档

## 1. 设计目标

Linly-Talker 的核心目标是将多模态对话能力串联为完整的数字人交互链路，覆盖：

- 语音输入
- 语音识别
- 大模型回复
- 语音合成
- 数字人口型驱动
- WebUI / API 输出

项目整体定位为多模型集成型研发框架，而不是单一模型推理脚本。

## 2. 总体架构

系统可以分为五层：

### 2.1 交互层

- `app.py`
- `webui.py`
- `app_talk.py`
- `app_img.py`
- `app_multi.py`

职责：

- 提供 Gradio 页面
- 组合各类参数与模型选项
- 承接用户上传的图片、语音、文本

### 2.2 编排层

入口文件中的 `LLM_response`、`TTS_response`、`Talker_response` 负责业务串联：

- 文本问题进入 LLM
- LLM 输出进入 TTS
- TTS 输出音频进入 Talker
- Talker 输出视频返回前端

这部分是当前项目的核心流程胶水层。

### 2.3 能力层

- `LLM/`：大语言模型封装
- `ASR/`：语音识别封装
- `TTS/`、`VITS/`：语音合成与语音克隆
- `TFG/`：数字人生成

其中：

- `LLM` 提供文本生成与多轮对话
- `ASR` 提供语音转文本
- `TTS` 提供文本转音频
- `TFG` 提供音频驱动人脸或人物视频生成

### 2.4 模型与算法层

典型模型包括：

- LLM：Linly、Qwen、Gemini、ChatGPT、ChatGLM
- ASR：Whisper、FunASR、OmniSenseVoice
- TTS：EdgeTTS、PaddleTTS、GPT-SoVITS、CosyVoice、XTTS
- Avatar：SadTalker、Wav2Lip、Wav2Lipv2、MuseTalk、NeRFTalk

### 2.5 服务层

- `api/tts_api.py`
- `api/llm_api.py`
- `api/talker_api.py`

职责：

- 将能力拆分成可独立部署的接口
- 方便前后端分离和分布式部署

## 3. 关键流程设计

## 3.1 文本对话生成流程

1. 用户输入文本
2. `LLM_response` 调用 `llm.generate`
3. 获取回答文本
4. `TTS_response` 生成音频
5. 返回音频或继续进入视频生成

## 3.2 语音对话流程

1. 用户录音或上传语音
2. `Asr` 调用 `asr.transcribe`
3. ASR 结果进入 LLM
4. 回答文本进入 TTS
5. 音频进入 Talker 输出视频

## 3.3 数字人视频生成流程

1. 输入角色图片或视频
2. 生成驱动音频
3. 选择 SadTalker / Wav2Lip / MuseTalk 等模型
4. 输出带口型的视频

## 4. 配置设计

集中配置文件为 `configs.py`，包含：

- 服务监听地址
- 端口
- 运行模式
- 默认模型路径
- HTTPS 证书路径

设计上采用“代码默认值 + 前端参数”的方式，优点是容易启动，缺点是配置中心能力较弱。

## 5. 模块设计特点

### 5.1 多模型并存

同一功能允许接入多个模型，便于对比效果和迭代研发。

### 5.2 前端驱动型编排

大量流程在 Gradio 页面入口中直接完成编排，适合快速实验和演示。

### 5.3 能力拆分 API 化

TTS、LLM、Talker 已经拆成独立接口，便于后续服务化。

### 5.4 兼顾在线与离线模式

- 在线：如 EdgeTTS、Gemini、ChatGPT
- 离线：如 PaddleTTS、本地 Qwen、Whisper

## 6. 当前设计优势

- 功能覆盖面广
- 试验速度快
- 模型替换成本低
- 适合教学、研究和方案验证

## 7. 当前设计局限

- 编排逻辑与界面逻辑耦合较深
- 配置分散，环境依赖较重
- 模型首次加载成本高
- 自动化测试和统一日志体系较弱
- 多模块并发下显存管理压力较大

## 8. 后续演进方向

- 将编排逻辑下沉为独立 service 层
- 引入统一配置文件或环境变量体系
- 将模型加载改造成插件化与懒加载
- 完善任务队列、缓存和异常恢复能力
- 增加链路监控与压测能力
