# LiveTalking 设计文档

## 1. 设计目标

LiveTalking 面向实时流式数字人场景，核心目标是提供一套低延迟、可打断、可扩展的数字人交互架构，支持文本或语音驱动，并可通过 WebRTC、RTMP、虚拟摄像头等方式输出。

## 2. 总体架构

系统可以分为六层：

### 2.1 接入层

- 浏览器页面：`web/` 或静态页面入口
- HTTP API：`/offer`、`/human`、`/humanaudio` 等

职责：

- 接收用户文本、音频和会话请求
- 向前端提供控制入口

### 2.2 会话层

- `server/session_manager.py`
- `server/rtc_manager.py`

职责：

- 分配 `sessionid`
- 管理最大并发会话数
- 维护会话生命周期
- 负责 WebRTC 建链与释放

### 2.3 编排层

- `server/routes.py`
- `server/avatar_routes.py`
- `server/task_manager.py`

职责：

- 解析业务请求
- 调用 TTS、LLM、Avatar 模块
- 管理录制、打断、任务创建等行为

### 2.4 能力层

- `avatars/`：数字人驱动模型
- `tts/`：TTS 插件
- `llm.py`：大模型响应
- `server/asr_server.py`：本地 ASR 支持

职责：

- 完成语音、文本和头像驱动能力

### 2.5 输出层

- `streamout/`

输出方式包括：

- WebRTC
- RTMP
- 虚拟摄像头
- RTCPush

### 2.6 插件注册层

- `registry.py`

设计上定义了插件类别：

- `stt`
- `llm`
- `tts`
- `avatar`
- `output`

通过 `register` 和 `create` 解耦模块创建过程，便于扩展新模型和新输出方式。

## 3. 主流程设计

## 3.1 服务启动流程

1. `app.py` 调用 `config.parse_args()`
2. 根据 `--model` 动态导入 avatar 模块
3. 执行 `load_model`、`load_avatar`、`warm_up`
4. 初始化 `session_manager`
5. 初始化 `RTCManager`
6. 注册 API 路由并启动 aiohttp 服务

## 3.2 WebRTC 交互流程

1. 前端请求 `POST /offer`
2. 服务端创建 `RTCPeerConnection`
3. 分配 `sessionid`
4. 绑定 avatar session
5. 返回 WebRTC `answer`

## 3.3 文本驱动流程

1. 请求 `POST /human`
2. 根据 `type` 选择 `echo` 或 `chat`
3. 如为 `chat`，调用 LLM 获取回复
4. 调用 TTS 生成音频
5. Avatar 模块同步口型
6. 通过输出层推送音视频

## 3.4 音频驱动流程

1. 请求 `POST /humanaudio`
2. 服务端接收音频文件
3. 音频直接进入 avatar 驱动链路
4. 输出流发送到前端或目标通道

## 4. 配置设计

`config.py` 支持两级配置：

- CLI 参数
- YAML 配置文件

优先级：

- CLI 参数 > YAML 配置 > 代码默认值

这样既方便单机调试，也适合部署时使用配置文件统一管理。

## 5. 模块设计亮点

### 5.1 动态模型加载

`app.py` 根据 `opt.model` 动态导入：

- `avatars.musetalk_avatar`
- `avatars.wav2lip_avatar`
- `avatars.ultralight_avatar`

减少了主入口对具体实现的硬编码。

### 5.2 全局 Avatar 缓存

`global_avatars` 用于缓存已加载 avatar，避免重复加载，提高多会话启动效率。

### 5.3 会话隔离

每个会话会构造独立的 avatar session，并允许传入：

- `avatar`
- `refaudio`
- `reftext`
- `custom_config`

适合多用户并发场景。

### 5.4 插件式扩展

`registry.py` 为后续扩展：

- 新 TTS
- 新 Avatar
- 新 Output

提供了统一入口。

## 6. 当前设计优势

- 实时交互链路清晰
- 传输方式丰富
- 插件化方向明确
- 会话与路由拆分较清楚
- 适合逐步演进成生产服务

## 7. 当前设计局限

- `app.py` 仍承担较多启动与装配逻辑
- 监控、鉴权、配置中心能力较弱
- 部分状态保存在进程内，不利于分布式扩展
- 自动化测试覆盖有限

## 8. 适用场景

- AI 数字人客服
- 实时互动讲解
- 直播带货数字人
- 语音助手可视化输出
- 远程演示与展示终端
